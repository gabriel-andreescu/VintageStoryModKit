# Deployment and packaging

## Package composition

Each mod target declares its package contents:

```lua
target("MyMod", function()
    add_rules("@addon/vsmk/mod", { project = "src/MyMod/MyMod.csproj" })
    add_installfiles("$(projectdir)/modinfo.json")
    add_installfiles("$(projectdir)/(assets/**)")
end)
```

The rule builds the C# project's `VsmkStage` target. It stages the mod assembly,
its runtime dependencies and the settings descriptors generated by VSMK, and
lists them in `.vsmk-files`. XMake copies only those entries, so files left
behind in the stage directory do not ship. Game assemblies remain compile-time
references. The [settings runtime](settings.md#reference-the-runtime) is merged
into the mod assembly that uses it, and its license notices are staged under
`licenses/`. Symbol and XML documentation files do not ship.

Add other files with XMake's `add_installfiles`, and ship other targets'
installable outputs with `targets`:

```lua
target("Companion", function()
    set_kind("phony")
    on_build(function(target)
        -- Produce build/companion/companion.exe.
    end)
    add_installfiles("build/companion/companion.exe")
end)

target("MyMod", function()
    add_rules("@addon/vsmk/mod", {
        project = "src/MyMod/MyMod.csproj",
        targets = { "Companion" },
    })
    add_installfiles("$(projectdir)/modinfo.json")
    add_installfiles("$(projectdir)/(assets/**)")
end)
```

`targets` adds build dependencies and collects each listed target's installable
outputs. Targets added only with `add_deps` do not ship. The staged C# output
comes first, followed by the listed targets in order and then the mod's own
`add_installfiles` mappings. Later mappings replace files at the same
destination. Several mods can list the same target. `.gitkeep` files are
omitted.

| Option          | Default                     | Purpose                                                                |
| --------------- | --------------------------- | ---------------------------------------------------------------------- |
| `project`       | Required                    | C# project that builds and stages the mod.                             |
| `configuration` | `Release`                   | Build configuration of the C# project.                                 |
| `targets`       | `{}`                        | Build targets whose installable outputs ship.                          |
| `package_name`  | `modid` from `modinfo.json` | ZIP filename before the version suffix.                                |
| `changelog`     | Root `CHANGELOG.md`         | [Release notes](github-actions.md#target-changelogs) for this package. |

## Deployment

Set mod destinations in the ignored `.xmake/vsmk/deploy.json` file:

```json
{
  "MyMod": ["C:/Users/Me/AppData/Roaming/VintagestoryData/Mods/MyMod"]
}
```

Use full target names, including namespaces. Paths are absolute or relative to
the project root. Each mod accepts multiple destinations. Give each mod its own
destination directory.

Build the mod or the project:

```powershell
xmake MyMod
xmake
```

Building a mod prepares its current files and deploys it to configured
destinations. Targets without destinations are not deployed. Disable deployment
with `xmake f --deploy=n`.

Rebuilds remove obsolete files previously deployed by that mod. Conflicts with
another mod or unowned files fail before deployment changes its destinations.

Ownership records live in `.vsmk/deployment.lua`, independently of XMake's
cache. After removing `.xmake/`, restore `deploy.json` to resume deployment.
Removing a destination leaves its files in place. Keep `.vsmk/` while its
outputs are deployed. If ownership records are lost, remove the project's
previously deployed files or choose an empty destination.

## ZIP packages

```powershell
xmake package
```

The ZIP contains the same clean payload used for deployment. Its default path is
`build/dist/<target>/<name>-<version>.zip`. Override the distribution root with
`xmake f --distdir=dist`.

The packaged `modinfo.json` supplies the default ZIP basename (`modid`) and
version. `package_name` changes the ZIP basename without changing the project,
assembly or mod ID.

Packaging replaces a target's ZIP and removes its older versions. Other targets
and unrelated files are preserved. Changing the distribution directory leaves
earlier output in place.
